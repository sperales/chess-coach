# Chess Coach 1.5.1 - Technical design

## Architecture

`PositionAnalysisService` is the single interactive position-analysis entry point. It wraps the existing `StockfishRunner`, interactive profile and `training_scenario_engine_cache`. `TrainingScenarioEngine` remains a compatible adapter so existing Scenario code does not fork the engine integration.

The shared API accepts strict FEN input and supports:

- `validate`: validate and normalize a complete FEN;
- `moves`: return legal UCI moves and SAN labels;
- `apply`: apply one legal UCI move and return the resulting FEN;
- `analyze`: return score, mate information, bestmove and normalized PV.

All state-changing API requests require CSRF. The server remains authoritative for move legality.

## Reuse order

1. Review's stored `bestmove` and `pv_before_uci`.
2. Compatible result in `training_scenario_engine_cache`.
3. Fresh interactive Stockfish search.

The existing cache table intentionally remains unchanged in 1.5.1. Its scenario-oriented name is legacy naming, not a separate cache implementation.

## PV normalization

PV moves are validated sequentially from their preceding FEN. Invalid tails are discarded. Each valid item contains UCI, SAN, `fen_before` and `fen_after`. The configured minimum is waived only for terminal positions.

## Client state

The Variation and Analysis Board clients use a small in-memory tree. Each node contains its parent, children, move, FEN and optional analysis. Navigation never mutates an existing ancestor; moving from a previous node creates or selects a child branch.

Requests use `AbortController` plus a monotonically increasing sequence. Only the latest sequence may update the visible board. Scenario uses the same stale-response rule while keeping its existing server-side run state.

## Evaluation point of view

Stockfish scores are returned from side-to-move and white points of view. Clients select a labelled point of view rather than applying implicit sign changes. Mate score and distance are separate fields.

## Observability

Interactive failures are logged with feature name, FEN hash, action and public error category. Successful cache hits and fresh searches are not logged per engine line, preventing shared-hosting log noise.

## Test traceability

The acceptance matrix covers: Best policy and restoration; FEN/legal/SAN edge cases; stored/cache/fresh PV; branching/history; white/black and mate point of view; Scenario accepted/rejected/alternative paths; request cancellation and stale responses; mobile/desktop controls and exact Review return context.
