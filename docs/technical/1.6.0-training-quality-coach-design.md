## Design principles

- Keep PHP, MariaDB, vanilla JavaScript and the existing queue/cron model.
- Add a pedagogical domain upstream of current Flash and Scenario delivery.
- Prefer immutable/versioned evidence over rewriting historical conclusions.
- Keep legacy selection authoritative while mode is `shadow`.
- Make every batch bounded and resumable for shared hosting.

## Existing architecture reused

- `game_analysis` and `game_move_analysis` remain the analysis source.
- Smart Tags remain detection evidence, not the v1.6 taxonomy itself.
- `training_exercises` and `training_scenarios` remain delivery projections.
- `training_solve_runs`, `training_scenario_runs`, hints, attempts and events supply behavioral evidence.
- `training_sessions` and `training_session_items` remain the plan execution model.
- Player DNA remains longitudinal evidence.
- `coach.php` becomes a consumer of the new domain instead of independently choosing a competing focus.
- Existing Nova helpers, sprite and core assets are extended rather than replaced.

## Domain services

New PHP modules use functions consistent with the current codebase:

- `training_taxonomy.php`: concepts, mappings and confidence evidence.
- `training_opportunities.php`: candidate creation, sources, currency and projection.
- `training_canonical.php`: normalized FEN, objectives and canonical hashes.
- `training_quality.php`: hard filters and Pedagogical Score.
- `training_selection_v2.php`: priority, reasons, shadow and comparisons.
- `training_mastery.php`: mastery, recent performance and review scheduling.
- `coach_decision.php`: single focus decision and reassessment.
- `training_composer_v2.php`: duration-aware composition and simple adaptation.
- `training_metrics.php`: bounded aggregates and rollout diagnostics.

Names may be consolidated where it reduces duplication, but dependency direction remains:

```text
analysis/tags
  → taxonomy/opportunities/quality
  → mastery/recent performance
  → coach decision
  → selection/composer
  → existing session delivery
  → evidence updates
```

## Schema

Migration `037_changes_1.6.0.sql` introduces the foundation. Exact SQL must also be reflected in `sql/install.sql`.

### `training_concepts`

Stable code, Spanish label, description, taxonomy version and active flag. Seed exactly ten v1 concepts idempotently.

### `training_concept_mappings`

Maps a signal type/key to a concept, role tendency, confidence contribution, evidence metadata and mapping version. Initial signals include Smart Tags, exercise/scenario types, phase and analysis classifications.

### `training_opportunities`

Contains ownership, canonical hash, normalized FEN, side, objective code/data, primary concept, confidence, estimated difficulty, recommended format, Pedagogical Score components/total, publication state, rejection reason, currency state and algorithm versions. The canonical key is unique per user and versioned identity.

### `training_opportunity_concepts`

Primary/secondary concept links with confidence, evidence JSON and taxonomy/mapping versions. Enforce one primary in service logic and at most two secondary links.

### `training_opportunity_sources`

Links an opportunity to game, analysis, move analysis and optional legacy exercise/scenario. Stores source side, recurrence evidence, source validity and timestamps. Unique source identity prevents duplicate attachment.

### `training_opportunity_audits`

Append-only bounded audit rows for candidate/filter/score/canonicalization transitions. Stores codes and structured values, not verbose engine output.

### `training_selection_runs` and `training_selection_items`

One run records user, mode, legacy/v2 versions, pool statistics and comparison summary. Items store rank, opportunity, selected-by-legacy/v2 flags, priority components, structured reason and evidence. Shadow runs do not create or reorder session items.

### `training_concept_mastery`

Current materialized state per user/concept with state, confidence, recent-performance state, evidence counts, autonomy, delayed-review evidence, pending-review flag and calculation versions.

### `training_mastery_events`

Append-only transitions and recalculations with previous/new values and evidence summary. Unique event keys make result processing idempotent.

### `coach_decisions`

Stores current and historical decisions, primary/secondary focus, score components, reason, evidence, objective, confidence and reassessment thresholds. At most one current row per user is enforced transactionally.

### Existing-table additions

- Optional `opportunity_id` on exercises, scenarios and session items.
- Structured `selection_reason_code` and version fields on session items while retaining human-readable `reason` for compatibility.
- `first_move_at`/`time_to_first_move_ms` on Flash and Scenario run evidence where the current model cannot derive it reliably.
- Review scheduling/version fields where required by the mastery model.

Foreign keys use existing ownership boundaries and safe `SET NULL` for delivery projections where historical evidence must survive.

## Analysis currency

Current analysis is resolved by the latest completed, structurally valid analysis for the owned game. The resolver returns identity plus an analysis fingerprint based on engine profile and relevant move data. Opportunity sources record this fingerprint.

On completed reanalysis:

1. mark older sources stale;
2. build/revalidate candidates from the current analysis;
3. attach equivalent current sources to the canonical opportunity;
4. retain an opportunity if its accepted solution/objective remains valid;
5. otherwise mark it inactive or superseded;
6. never delete prior source or audit rows.

## Canonical identity

FEN normalization excludes halfmove/fullmove counters but retains castling and en-passant state. Moves are lowercase UCI, deduplicated and sorted only for hashing. Objective data is normalized to stable JSON. The SHA-256 hash includes canonical schema version so identity rules can evolve without rewriting history.

Exact duplicates merge sources. Basic similarity uses deterministic position/objective features only to apply redundancy and same-session penalties; it does not merge uncertain records.

## Candidate and quality pipeline

Each current analyzed move produces zero or more candidates. Taxonomy mapping calculates concept confidence and evidence. Hard filters return the first stable rejection code plus all matching evidence. Only survivors receive component scores.

The score service returns all components, total, state and version. Constants live in one configuration function/module and are covered by fixtures. No UI recalculates filters or scores.

## Selection modes

`config/app.example.php` documents `training_selection_mode` with allowed values `legacy`, `shadow`, `active`; absent or invalid values resolve to `shadow` for v1.6.0 after migration/deployment confirmation, while explicit `disabled` resolves to `legacy`.

- `legacy`: current Coach/selector only.
- `shadow`: build the legacy plan normally, calculate v2 against the same point-in-time context and persist comparison.
- `active`: v2 selection and Composer create session items; legacy may still be calculated for bounded comparison during rollout.

Shadow failures are isolated and cannot prevent Training from loading or starting.

## Delivery projection

Published opportunities are projected lazily or during bounded backfill into existing Flash/Scenario records. The opportunity owns concept, objective and valid solutions; delivery records keep the fields required by existing APIs. Projection is idempotent by opportunity and format version.

## Mastery evidence

Only evidence with reliable run identity, timestamps and hint/attempt outcome is eligible. Pre-foundation historical attempts are not fabricated. Existing v1.4.12+ solve runs and Scenario runs may be included when they can be mapped to a canonical opportunity and algorithm version.

Recalculation is deterministic from eligible events. Current mastery is materialized for fast reads; transition events remain append-only. Recent Performance is calculated from the most recent five relevant results or 30-day window.

Deferred review is a centralized deterministic rule returning due date, interval, reason and version. A due review becomes selection evidence, not an unconditional exercise.

## Coach Decision

The decision service gathers one snapshot of DNA, mastery, recent performance, recurrence, recent games and available published opportunity counts. It persists score components and a decision version. Existing Home, Training, plans and Nova read the current decision through one public payload.

Reassessment is idempotent and occurs when no decision exists or any persisted threshold is met. Low-confidence and unavailable-content guards run after scoring.

## Composer

The Composer accepts duration profile, Coach Decision, eligible selection rows and recent session context. It fills constrained buckets in priority order, rejects near duplicates and stops early when no quality item remains. Format targets are preferences, never quotas.

Session items persist opportunity identity, reason code, evidence and algorithm versions. Simple adaptation may replace only pending items and records the reason; completed/active items never change.

## Result processing

Flash and Scenario completion emit a normalized training result containing opportunity, concept, result, attempts, highest hint, first-move time, total duration, estimated difficulty and session context. One idempotent handler updates:

1. review schedule;
2. Recent Performance;
3. Mastery materialization/events;
4. session completion evidence;
5. Coach reassessment counters;
6. Nova comparison facts.

## Streak and goals

A normalized valid-activity query counts finalized attempted Flash/Scenario activity per calendar day. Streak uses that query. Daily and weekly goals keep their configured progress rules. Historical days are interpreted conservatively from reliable finalized runs.

## Nova reactive behavior

The server emits semantic states; JavaScript changes `data-nova-state` on real events. State-to-asset mapping is centralized:

- idle → neutral;
- thinking → thinking;
- correct/session complete → success;
- error → error;
- hint → warning;
- explaining → focus.

CSS uses the current six-cell sprite. Correct uses one small scale/elevation pulse; error uses a minimal horizontal response; thinking uses a restrained loop only while work is pending; session completion uses a one-shot double pulse. The core color follows state. `prefers-reduced-motion` disables transforms and loops while retaining expression, color and text. No new visual material is required for v1.

## Backfill

Backfill runs in small user-scoped batches with cursor, status, counters, timestamps and last public error. It is safe to repeat and never holds a transaction across engine work. Stages are taxonomy mapping, opportunity creation, currency, canonical attachment, quality scoring, optional projection and mastery recalculation.

It reuses stored analysis. Records requiring fresh engine evidence are left rejected/reserve with an explicit reason; they are not automatically reanalyzed.

## Observability

Database audit tables are authoritative for domain decisions. Application logs only summarize batch/run failures using user ID, run ID, stage and public category. No PGN, complete FEN, engine PV or large evidence payload is duplicated in logs.

## Security and compatibility

- Every query remains scoped by authenticated user ownership.
- New state-changing API actions require existing CSRF handling.
- Structured JSON is encoded server-side and escaped in HTML.
- No user input reaches shell commands.
- Legacy paths remain unchanged in shadow mode.
- Missing new tables/config during a partial deploy fail back to legacy selection rather than breaking Training.

## Test strategy

Add dependency-free contract fixtures for taxonomy, filters, score, canonicalization, selection shadow isolation, routing, difficulty, mastery, Coach Decision, Composer, streak and Nova states. Add schema/migration assertions and extend end-to-end layout/API contracts. Run the existing PHP suite, JavaScript syntax checks, encoding checks and manual shared-hosting smoke checklist.
